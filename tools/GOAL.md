두 트랙을 번갈아 진행한다. 공통 자산이 하나 있다: **라이다로 다른 차를 보는 것**. MPC 트랙에서는

# 트랙 1 — SW+AI (MPC 레이싱)

## 채점이 무엇인지

Elo 배틀: **challenger + ranker + NPC("Computer")**, 6 랩 필요, **480 초** 제한, 순위로 레이팅 이동.
보드 배틀 40 건 중 **34 건이 랩 수로 갈린다.** 0 랩·4 랩 완주가 흔하고 랭킹 9·12 위 팀도 4 랩에서
멈춘다. **완주가 1 순위, 총시간은 랩 동수일 때만 작동하는 타이브레이크.**

우리: 일반부(코스 2), 레이팅 734, 코스 2 내 22/60. 넘어야 할 1 위 CRESCendo 810.
참고 페이스: KSK(학생부 1 위) 6 랩 282.155 초, 최고 랩 44.010.

## 목표

| | 현재 최선 | 목표 |
|---|---|---|
| 480 초 내 6 랩 완주율 | 9/12 (75%) | **12/12** |
| 완주시 총시간 | 347.5 평균 / 285 최고 | 평균 **320 이하** |
| 교착 사건 | 레이스당 다수 | **0** |

## 페이스는 이미 끝났다

교착이 한 번도 없는 실행은 랩당 46.7 초, 5 랩 233.5 초 — **6 랩 환산 280 초로 KSK 의 282.155 를
넘는다.** 남은 손실 전부가 교착이다. 교착 1 건이 약 40 초.

## 확립된 것

`stuck_recovery_controller.cpp:127` 이 `command.longitudinal.speed < 1.0` 이면 빠져나간다. QP 가
실행 불가능해지면 MPC 는 0 을 명령하므로 **복구 노드가 존재하는 이유인 상황을 복구 노드가 볼 수
없다.** 실측: 랩 3 을 t+164 초에 끝낸 실행이 391 초를 명령속도 0.0 / 정지감지 0 회로 서 있었다.

교착 차단(정지 상태에서 일정 시간 후 1.5 m/s 명령)으로 12 레이스 랩 합이 **32 -> 68** 이 됐다.
이전 제출본은 **그리드 슬롯 3 에서만 완주한다**(4/4, 나머지 2/8).

480 초 기준 완주율은 구제 발동 지연에 단조롭게 반응한다: `TICKS` 20 -> 7/12, 40 -> 9/12, 70 -> 9/12.
반대 방향(`fast-escape`, 0.2 초 3.0 m/s)은 구제 498 회로 최악. **급하게 빼내면 스래싱이 된다.**
`FUNNEL_RATE` 는 0.15 가 0.25 와 0.08 을 모두 이긴다 — 깔때기는 열되 닫는 힘이 필요하다.

## 남은 레버

1. 교착 사건 수를 0 으로. 지금은 탈출을 개선했을 뿐 발생을 막지 못했다.
2. NPC 대응. NPC 는 **v2x 에 절대 안 실린다**(실측: 2 대 + NPC 구성에서도 v2x 는 2 건만 보고).
   라이다만 본다. `lidar_guard` 가 체인에 있으나 NPC 가 있는 조건에서 측정된 적이 없다.

## 재시험 금지 (전부 실측)

라인: 우리 336.1 대 KSK 이식 352.3 — KSK 라인은 우리 제어기에서 118.64 초. 그들의 반전이 더
급하다(dkappa/ds 0.053 대 0.038). 우리 라인이 더 낫다.
조향 변화율: 0.25 / 0.50 / 0.70 / 1.40 전부 0.35 보다 나쁘다. low-pass 게인이 둘 다 1.0 이라
하류 감쇠가 없다.
구간 속도: 상한 올리기 3 회 실패, 하한 22->26 실패, s5 30->26 무차별.
Q / QN / N / wp_id_offset: 무차별 또는 악화. R[1] 은 튜닝 대상이 아니다 — 입력 기준 ur 이 0 이라
R[1]>0 은 조향 자체에 벌점(측정: 완주 0 랩, 복구 112·115 회).
3 대 동시로 1 초짜리 파라미터 차이 측정: 불가능. 이 16 코어 박스에서 챔피언 자신의 편차가 103 초.
랩 수 같은 큰 효과만 3 대로 잴 수 있다.
총시간 평균의 세대 간 비교: 불가능. 같은 설정이 313.6 과 348.4 를 낸다. 같은 레이스 안의 순위만
유효하다.

# 트랙 2 — AI 트랙 (End-to-End)

## 제출물

Google Form 으로 두 개: **개발 내용 슬라이드**(용량 제한 주의) + **주행 영상**(공개될 수 있음).
결과는 이메일 통보, 우수 팀 영상은 공개.

## 슬라이드 필수 5 항목

1. 주행 데이터 첨부
2. **다른 차량에 대한 회피 및 정지 고려** <- 트랙 1 의 NPC 문제와 같은 문제
3. 모델 아키텍처 설명
4. 학습 데이터 및 평가 내용
5. 팀의 독창성 및 주력 포인트

## 강화학습은 필요 없다

요구는 "End-to-End AI 모델"이고 TinyLidarNet 은 **지도학습(behavioural cloning)**이다. 공식 README
가 명시한다: `LaserScan`(입력) + `AckermannControlCommand`(교사) 를 담은 rosbag -> extract -> train.
**우리 MPC 가 곧 교사**이고 46 초로 잘 도니 라벨 데이터를 무한히 만들 수 있다.
`ml_workspace/reinforcement_learning/` 은 옵션이지 필수가 아니다.

## 이미 있는 것

```
tiny_lidar_net/   1D CNN (conv 5 + fc 4), input_dim 750, output [accel, steer]
                  train.py / extract_data_from_bag.py / convert_weight.py 완비
pilot_net/        이미지 기반 별도 파이프라인
ckpt/tinylidarnet_weights.npy   602 KB, 2026-07-28 학습됨
                  백업 bak_pre_hairpin_finetune / bak_pre_round4 -> 파인튜닝 이력 있음
control_method: tiny_lidar_net | pilot_net | rl_train 모두 런치 연결됨
```

`input_dim: 750` 이 실측 스캔 빔 수와 정확히 일치한다. 이 시뮬레이터로 학습된 모델이다.

## 갭 두 개

1. **입력이 라이다 단독.** 요구는 2D LiDAR + 이미지 + 차속. 차속은 스칼라 하나 붙이면 되고,
   README 가 적어둔 "가속 학습이 안 됐다"의 유력한 원인이다 — 현재 속도를 모르면 가속 목표를 못 낸다.
2. **학습 데이터가 없다.** `dataset/`, `checkpoints/`, `rawdata/` 전부 비어 있다(gitignore).
   가중치만 남고 데이터는 사라졌다.

## 목표

| | 현재 | 목표 |
|---|---|---|
| 학습 rosbag | 0 | **20 랩 이상** (MPC 교사, 라이다 on) |
| 모델 입력 | 라이다만 | **라이다 + 이미지 + 차속** |
| accel 학습 | 실패 기록 | 차속 입력으로 재시도 |
| 완주 (AI 제어) | 미측정 | 6 랩 완주 1 회 이상 |
| 슬라이드 | 없음 | 5 항목 골격 |

## 데이터는 레이스에서 공짜로 나온다

`battle3.sh` 가 `--lidar cpu` 로 돌고 있고 실측 20 Hz 다. 레이스에 rosbag 기록만 켜면 트랙 1 의
스크리닝이 곧 트랙 2 의 학습 데이터 수집이 된다. 두 트랙이 같은 실행을 공유한다.

### 2026-08-01 정정 — 레이스 bag 은 학습 데이터로 거의 못 쓴다

`output/npc-with-{1,2,3}/bag` 에 이미 549 초짜리 3 개가 있었다(스캔 32,932 = 27.4 분). 그러나
**실측 속도 0.5 m/s 미만이 68%** 다. 위의 "랩 3 을 t+164 초에 끝내고 391 초를 서 있었다" 가 데이터
전체의 성격이다. 이 프레임을 복제하면 네트워크는 **서 있기를 배운다.**

`--min-speed 2.0` 으로 실제 주행만 남기면 **5,483 샘플 = 4.6 분**. 20 랩(약 15.3 분) 목표에
**10.8 분 부족**하다. 즉 레이스 bag 은 회피 행동 샘플로만 값이 있고, 주행 라벨은 `solo6lidar.sh`
(6 랩 clean, 막을 NPC 가 없음, 실행당 약 4.6 분)로 3 회 더 받아야 채워진다.

### 2026-08-02 — solo 수집 1회로 데이터 목표 달성, 새 기본값은 페이스 중립

`tools/collect_teacher_data.sh`(경계가 있는 solo6lidar 수집 러너)로 1회 실행:
**14,093 샘플 = 11.7 분, `--min-speed 2.0` 통과율 100%**. 레이스 bag 이 83% 정지였던 것과
대비되며, "solo 는 막을 NPC 가 없으니 전 프레임이 유효 라벨"이라는 가정이 확인됐다.
누적 **19,576 샘플 = 16.3 분**으로 20 랩(약 15.3 분) 목표 **달성**.

스캔 750 빔 전부 유한, 0-range 빔 없음, 조향 ±0.495 rad 로 포화 0 건(한계 0.64).

같은 실행이 트랙 1 측정도 준다 — **새 기본값(TICKS 40 / FUNNEL_RATE 0.15) 솔로 6 랩**:

```
47.53 / 46.27 / 45.96 / 46.12 / 46.36 / 46.46   평균 46.45  최고 45.96  총 278.68s  6/6
```

문서화된 기준선(평균 46.53 / 최고 46.05)과 −0.08s 차이로 **사실상 동일**. 즉 funnel +
antideadlock 은 **솔로 페이스를 깎지 않고** 완주율을 산다 — 이게 이 변경의 전제였고 이제 측정됐다.
(총 278.68s 를 KSK 의 282.155s 와 직접 비교하지 말 것: 이쪽은 `--handicap off` 솔로이고
저쪽은 핸디캡·트래픽이 있는 배틀이다. 기준선 46.53s 와의 비교만 apples-to-apples 다.)

수집 러너에서 배운 것(같은 실수 반복 금지):

- **AWSIM 준비 판정은 컨테이너 안 `Player.log` 의 `state → Start` 로 하라.** `ros2 topic list`
  는 구독자만 있어도 토픽을 표시해서 AWSIM 부팅 중에 5 초 만에 오판한다(8KB 빈 bag).
  `ros2 topic echo` 는 `docker compose exec` 셸이 노드들의 RMW/cyclonedds 환경을 안 물려받아
  건강한 AWSIM 에서도 240 초 타임아웃 난다. `awsim.log`(stdout)에는 Unity 부팅 정보가 없다.
- **프로브의 stderr 를 버리지 말 것.** 2 차 실패의 원인이 안 보인 이유가 그것이다.
- `result-summary.json` 은 `LOG_DIR` 이 아니라 **`aichallenge/result-summary.json`** 에 쓰인다.
  세션 간 살아남으므로 반드시 시작 시점 mtime 을 기준선으로 잡아야 한다.
- AWSIM 은 6 랩 채점 후에도 차를 계속 달리게 한다(283 초에 완주, 705 초까지 주행). 교사 데이터엔
  그 초과 주행이 공짜 라벨이라 기본값은 계속 돌리는 것(`STOP_AT_RACE_END=0`)이고, 랩이 곧 측정인
  트랙 1 스크리닝에서는 켜라.

부수로 확인된 것:

- **명령 속도는 교착 판별에 못 쓴다.** 명령이 0 인 프레임은 7.1% 인데 실제 정지는 67.8% 다.
  컨트롤러는 낼 수 없는 속도를 계속 명령한다. 판별은 `velocity_status` 로만 된다 —
  그리고 그것이 위 "갭 1" 의 그 입력이다. 하나로 둘이 해결된다.
- 필터를 걸면 조향 범위가 ±0.52 rad 로 들어온다(차량 한계 0.64). 즉 앞서 본 포화 조향 0.9 rad
  은 전부 교착·이탈 프레임이었다.
- 세 bag 은 `metadata.yaml` 이 없었다(clean shutdown 없이 죽음). db3 에 topics·QoS·ros_distro·
  타임스탬프가 다 있어서 `tools/rebuild_bag_metadata.py` 로 복원했다. 이제 `ros2 bag play` 도 된다.
- `extract_data_from_bag.py` 버그 두 개를 고쳤다. (1) rosbags 기본 typestore 에 Autoware 타입이
  없어 db3 bag 의 control_cmd 가 **전량 조용히 스킵**되고 "insufficient data" 로 끝났다
  (mcap 은 스키마 내장이라 우연히 동작). IDL 을 `tiny_lidar_net/msgdefs/` 에 넣고 등록한다.
  (2) 출력 디렉토리 이름이 bag 의 basename 뿐이라, 세 bag 이 모두 `bag` 이므로 **서로 덮어써서
  3 개 중 1 개분만 남았다.** 그래도 "성공" 으로 보고됐다.
